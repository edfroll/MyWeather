# MyWeather: сверка Open-Meteo API

**Статус:** проверено. Факты об API, не решения.
**Дата проверки:** 13.10.2026
**Входной документ:** `docs/product-decisions.md` (дальше — «продукт»), §2.1–§2.5
**Потребители:** заказчик (Edward) — продуктовые развилки; агент-архитектор — шов источников, кэш, слой данных.

---

## 0. Как проверялось

- Документация — по исходному HTML страниц open-meteo.com, а не по пересказу: [Forecast docs](https://open-meteo.com/en/docs), [Historical Weather](https://open-meteo.com/en/docs/historical-weather-api), [Historical Forecast](https://open-meteo.com/en/docs/historical-forecast-api), [Pricing](https://open-meteo.com/en/pricing), [Terms](https://open-meteo.com/en/terms).
- Живые запросы к API — четыре города: Москва, Токио, Нью-Йорк, Берлин. Где город не указан, проверка шла по Москве.
- Числа «глубины данных» — снимок на 13.10.2026. Они плавают со временем и от точки к точке, константами в коде их делать нельзя.

## 1. Сверка

| # | Предположение в продукте | Статус | Как на самом деле |
|---|---|---|---|
| 1 | Forecast API: прогноз на 16 дней (§2.1) | ✅ | Документация: `forecast_days` 0–16, по умолчанию 7. С `16` данные приходят на 16 дней вперёд, с `17` — ошибка «Allowed range 0 to 16» |
| 2 | `past_days` до 92 дней (§2.1) | ✅ | Документация: 0–92. API принимает и 93, со `100` — ошибка «Allowed range 0 to 93». Опираемся на документированные 92 |
| 3 | Через `past_days` приходит недавнее прошлое на всю глубину (§2.4) | ❌ | Начало ряда — `null`, и его длина зависит от метрики и точки. Реальная глубина: температура 59–75 дней, `precipitation_probability` 57–82, `uv_index` 56–57. Все 11 метрик одновременно гарантированы только примерно на **55 дней** |
| 4 | Archive API: реанализ ERA5, глубина в приложении — 5 лет (§2.1) | ⚠️ частично | Эндпоинт `archive-api.open-meteo.com/v1/archive`, данные с 1940 года. Но **по умолчанию (`best_match`) в нашем окне отдаётся ECMWF IFS 9 км (с 2017), а не ERA5**: за 2023 и за 2026 год 72 из 72 часов совпадают с `models=ecmwf_ifs`, с `era5` — 0–4 из 72. Ограничение 5 лет вводим мы, у API его нет: запрос на 5 лет почасовых данных вернул 43 824 значения |
| 5 | Имена всех 11 полей (§2.2) | ✅ | Все 11 имён API принимает. `weather_code`, `is_day`, `sunrise`/`sunset` в `daily` тоже есть |
| 6 | Те же 11 метрик доступны в истории (§2.2, §2.3) | ❌, есть обход | В Archive API 9 метрик заполнены полностью (43 824 из 43 824), а `uv_index` и `precipitation_probability` — **0 из 43 824**. Обход — **Historical Forecast API** (`historical-forecast-api.open-meteo.com/v1/forecast`, формат как у Forecast API, доступен на Free): `uv_index` с **22–23.03.2021**, то есть на всё 5-летнее окно; `precipitation_probability` с **25.04.2024**, примерно 2,5 года (Москва и Нью-Йорк, одна и та же дата) |
| 7 | `timezone=auto` даёт местное время (§2.5) | ✅ | Получены зоны `Europe/Moscow`, `Asia/Tokyo`, `America/New_York`, `Europe/Berlin`. В ответе есть `utc_offset_seconds`. Без параметра время в GMT. Для `daily` параметр `timezone` обязателен |
| 8 | Единицы: запрашиваем СИ (§2.2, §7.1) | ✅ с уточнением | По умолчанию API отдаёт °C, мм, гПа, но **ветер — в км/ч**. С `wind_speed_unit=ms` ветер приходит в м/с, поэтому параметр передаётся **всегда** |
| 9 | Хвост архива (2–3 месяца) — предварительная ERA5T, потом уточняется (§2.4) | ❌ предпосылка не подтвердилась | ERA5T в документации не упоминается. ERA5 обновляется ежедневно с задержкой 5 дней (последнее значение `era5` — 08.10). Но по умолчанию архив отдаёт IFS, а IFS обновляется каждые 6 часов без задержки, данные есть до текущего дня. Пересчитываются ли задним числом значения IFS за последние дни, документация не говорит — **неизвестно** |
| 10 | Лимиты (подразумеваются в §6) | ✅ | Бесплатный тариф: 600 вызовов в минуту, 5 000 в час, 10 000 в день, 300 000 в месяц. Только некоммерческое использование, атрибуция CC BY 4.0. Historical Weather и Historical Forecast на Free **доступны** (в таблице Pricing у Free — ✅, ❌ только у Standard) |
| 11 | Вес запроса при длинном диапазоне (§6) | ✅ описан | Pricing: «Requests for data covering more than 10 weather variables or extending over a period of more than 2 weeks for a single location are considered multiple API calls», счёт дробный. 5 лет при ≤10 переменных ≈ **130 вызовов**, при 11 ≈ 143 |

## 2. Бюджет полной загрузки одной локации

| Источник | Что | Вес |
|---|---|---|
| Archive API | 5 лет, 9 метрик | ≈ 130 вызовов |
| Historical Forecast API | 5 лет `uv_index` (+ `precipitation_probability` с 25.04.2024, если она войдёт в историю) | ≈ 130 вызовов |
| **Итого** | | **≈ 260 вызовов**, это 2,6% дневного лимита |

Вывод: перекачивать историю целиком при каждом открытии нельзя. «Догрузка только недостающих кусков» (продукт §1.1, §6) — требование бюджета, а не оптимизация.

## 3. Что это меняет — на решение

1. **Шов прогноз/архив (продукт §2.4) — архитектору.** Порог в 92 дня не работает, гарантировано около 55 дней. Зато архив `best_match` непрерывен до текущего дня. Самый простой вариант: всё прошлое — из архива, Forecast API — только будущее. Решение за архитектором.
2. **УФ-индекс в истории — решаемо, архитектору.** Через Historical Forecast API данные есть на всё 5-летнее окно. Это третий источник в слое данных, но чипс «УФ-индекс» в истории можно оставить.
3. **Вероятность осадков в истории — Edward.** Данные есть только с 25.04.2024. Варианты: показывать с этой даты; убрать метрику из истории; ограничить для неё диапазон. Это продуктовое и UX-решение, оно затрагивает пару «температура + вероятность осадков» (продукт §4.1).
4. **Неизменность архива (продукт §6.1) — архитектору.** Механизма ERA5T нет. Пересчитывается ли IFS за последние дни, неизвестно. Для кэша безопаснее считать неизменным архив старше нескольких дней и перезапрашивать свежий хвост.

## 4. Правки в продукт — после согласия Edward

- §2.1: «реанализ ERA5» → «по умолчанию ECMWF IFS 9 км (`best_match`, с 2017); ERA5 — с 1940».
- §2.2: добавить «`wind_speed_unit=ms` передаётся всегда».
- §2.4: порог «92 дня» и оговорку про ERA5T переписать по итогам решений из раздела 3.
