# Open-Meteo: сверка API

**Статус:** факты API, проверены 13.10.2026: исходный HTML страниц документации (не пересказ) и живые запросы к API по четырём городам — Москва, Токио, Нью-Йорк, Берлин. Числа глубины данных — снимок на эту дату, константами в коде их делать нельзя.
**Потребитель:** агент-архитектор.
**Связь с продуктом:** проверяет предположения `product-decisions.md` §2.1–§2.5, §6, §7.1.
Продукт этот документ не переписывает. Где предпосылка продукта не подтвердилась, это помечено ❌ и вынесено в развилки (§7). До решения Edward продукт не меняется.

Легенда: ✅ подтверждено · ⚠️ частично · ❌ не подтвердилось · ❓ не проверялось.

## 1. Эндпоинты

| API | Хост | Что даёт | Статус |
|---|---|---|---|
| Forecast | `api.open-meteo.com` | `forecast_days` 0–16 (по умолчанию 7). `past_days` 0–92 по документации | ✅ |
| Historical Weather (Archive) | `archive-api.open-meteo.com/v1/archive` | Данные с 1940 года. Модель по умолчанию — см. §4 | ⚠️ |
| Historical Forecast | `historical-forecast-api.open-meteo.com` | Архив прогнозов, формат как у Forecast | ✅ |
| Geocoding | — | В этой сверке не проверялся | ❓ |

Детали:
- `forecast_days=16` возвращает данные до D+15; `17` даёт ошибку «Allowed range 0 to 16».
- `past_days`: документировано 0–92. API фактически принимает 93, на 100 отвечает ошибкой. **Опираемся на документированные 92.**
- Ограничение глубины истории в 5 лет — **наше** (продукт §2.3), у API его нет. Запрос на 5 лет почасовых данных вернул 43 824 значения на метрику.

## 2. Обязательные параметры запроса

| Параметр | Правило | Почему |
|---|---|---|
| `timezone=auto` | Передавать всегда | Ответ приходит в местном времени, с полями `timezone` и `utc_offset_seconds`. Без параметра время в GMT. Для `daily` параметр обязателен. Проверено на Europe/Moscow, Asia/Tokyo, America/New_York, Europe/Berlin |
| `wind_speed_unit=ms` | Передавать всегда | По умолчанию ветер приходит в км/ч. Остальные единицы по умолчанию уже СИ-совместимы: °C, мм, гПа |
| Прочие параметры единиц | Не передавать | Продукт §7.1: хранение в СИ, конвертация на отображении |
| `models` | Зависит от развилки OM-3 (§7) | По умолчанию (`best_match`) архив отдаёт не ERA5, см. §4 |

**Ключевой факт про `past_days` ❌.** Начало ряда приходит `null`. Длина пустого участка зависит от метрики и от города. Все 11 метрик одновременно гарантированы только примерно на **55 дней**, а не на 92. Замер сделан на нескольких городах; что 55 дней — нижняя граница для любого города, не доказано.

## 4. Модель данных архива ⚠️

- По умолчанию (`best_match`) в нашем 5-летнем окне архив отдаёт **ECMWF IFS 9 км** (данные с 2017 года), а **не ERA5**. Сравнение за 2023 и 2026 годы: 72 из 72 часов совпадают с `ecmwf_ifs`, с `era5` — 0–4.
- **ERA5:** обновляется ежедневно с задержкой 5 дней (на 13.10 последнее значение — 08.10).
- **IFS:** обновляется каждые 6 часов без задержки, данные есть до текущего дня.
- **ERA5T** в документации не упоминается. Предпосылка продукта §6.1 «хвост ~3 месяца — уточняемая ERA5T» не подтвердилась ❌.
- Пересчитываются ли задним числом значения IFS за последние дни — в документации не сказано ❓.

Следствие: формулировки продукта §2.1 («реанализ ERA5») и §6.1 («хвост архива ERA5T») не соответствуют тому, что API реально отдаёт. Решение — развилка OM-3.

## 5. Лимиты и бюджет вызовов ✅

**Тариф Free:** 600 запросов в минуту, 5 000 в час, 10 000 в день, 300 000 в месяц. Только некоммерческое использование. Атрибуция **CC BY 4.0** обязательна.

**Historical Weather API и Historical Forecast API доступны на Free.** В таблице Pricing у Free стоит ✅, ❌ стоит только у Standard. Любое утверждение «архив платный» — ошибка пересказа.

**Вес запроса** (Pricing): каждые 2 недели данных на одну точку = 1 вызов. Больше 10 переменных — пропорционально больше, считается дробно. Вес растёт с объёмом, но один HTTP-запрос — это минимум 1 вызов: «one API call corresponds to one HTTP API request». Поэтому крупный запрос дробить на куски короче 2 недель **невыгодно**, а частые мелкие дозапросы свежего хвоста стоят по 1 вызову каждый.

| Загрузка одной локации | Вызовов |
|---|---|
| 5 лет, ≤ 10 переменных | ≈ 130 |
| 5 лет, 11 переменных | ≈ 143 |
| Archive, 9 метрик, 5 лет | ≈ 130 |
| + `uv_index` из Historical Forecast, 5 лет | ≈ 130 |
| + `precipitation_probability` тем же запросом к Historical Forecast | +0 (2 переменные в одном запросе, вес по периоду) |

Полная история одной локации в зависимости от OM-2 — 130–260 вызовов, то есть 1,3–2,6 % дневного лимита.

**Требования, которые отсюда следуют:**
1. **Догрузка только недостающих кусков (продукт §6.4) — требование бюджета, а не только оптимизация.**
2. **Тесты не ходят в сеть.** Агентные сессии и CI гоняют тесты много раз; тесты работают на фикстурах ответов, иначе разработка расходует тот же дневной лимит.
3. **Атрибуция CC BY 4.0 нужна в UI.** В продукте и в UX места под неё нет — вопрос архитектору и UX (`roadmap.md` §4).

## 6. Открытые вопросы (не проверялось)

1. Пересчитывает ли архив IFS свежие дни задним числом — от этого зависит, сколько дней хвоста считать «уточняемым».
2. ✅ *Проверено 13.10.2026, 21:18 UTC (Москва, Нью-Йорк).* **Задержки нет**: Archive (`best_match` и `ecmwf_ifs`) и Historical Forecast отдают `temperature_2m` до 23:00 GMT текущих суток, то есть и на часы, которые ещё не наступили. Значит, свежий хвост архива — это прогнозные шаги IFS, а не наблюдения, и они почти наверняка будут перезаписаны (к вопросу 1). `end_date` в Archive — не позже текущей даты, завтра отклоняется. `uv_index` в Historical Forecast тоже есть до конца текущих суток.
3. ✅ *Проверено, 264 часа за последние 10 дней, Москва / Нью-Йорк.* **Скачок есть**: Forecast (`past_days`, `best_match`) и Archive (`ecmwf_ifs`) на одном и том же часе расходятся — температура в среднем 0,5 / 0,7 °C, максимум 2,1 / 2,5 °C; ветер в среднем 0,9 / 1,0 м/с, максимум 2,5 / 4,0 м/с; осадки — максимум 2,0 / 6,5 мм. Причина — разные модели в двух API. Шов внутри прошлого даст видимый излом на графике.
4. ✅ *Проверено на 01–02.06.2023.* `is_day`, `weather_code` (hourly) и `sunrise`/`sunset`, `weather_code` (daily) есть и в Archive, и в Historical Forecast. Значения `weather_code` между источниками могут различаться (51 против 80 за один и тот же день) — снова разные модели.
5. Geocoding API: поля ответа, язык выдачи (ru/en). Обратного геокодинга нет (UX п. 9) — здесь не перепроверялось.
6. Лимиты считаются на IP или иначе — в таблице не указано.
7. Покрытие остальных 9 метрик в Historical Forecast — понадобится, только если рассматривать историю целиком из него.
