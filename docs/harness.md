## 2. Путь «штаб решил → коммит» — вариант Б **[Edward]**

Jira работает как входящие. Штаб в репозиторий не пишет.

1. **Штаб** после решения Edward в чате создаёт тикет MW класса trivial с правками в формате before → after (§2.2).
2. **Edward** запускает облачную сессию: `/mw-docs-apply MW-n`.
3. **Сессия** выполняет проверки (§2.1), применяет правки в ветке, останавливается перед коммитом и ждёт Edward. Затем коммит, PR, комментарий в тикет (что применено, ссылка на PR), перевод статуса.
4. **Edward** мержит PR (squash, §3) и синхронизирует Context.
5. **Штаб** сверяет Context с тикетом. Если есть расхождения — новый тикет, а не правка задним числом.

Риск: Jira может испортить markdown в описании тикета — блоки кода, переносы строк, таблицы. Проверяется шагом 6 проверки коннектора (§8). Если испортит — правки кладутся вложением к тикету или в `docs/inbox/MW-n.md` **[открыто]**.

### 2.1 Проверки `mw-docs-apply`

Решено **[Edward]**:
1. **«Было» совпадает дословно** — с переносами строк и пробелами — и ровно в одном месте файла. Иначе стоп: в комментарий к тикету записывается, какой блок не совпал и что сейчас стоит на его месте. Дальше решает Edward.
2. **Новый факт — только со ссылкой на источник:** § документа, URL, файл в `docs/research/`, коммит.
3. **Непроверенное не записывается как факт.** Оно помечается ❓, «почти наверняка» или «проверка ДД.ММ».

Предлагается дополнительно **[штаб]**:
4. **Всё или ничего.** Если хоть один блок не прошёл проверку 1, не применяется ни один. Частично применённое решение хуже, чем неприменённое.
5. **Свои правки «Стало» не делать.** Если «Стало» кажется неверным, сессия записывает замечание в комментарий и всё равно применяет как есть либо останавливается — третьего пути нет. Пример: в c4aa137 блок B2 разошёлся с текстом, и его применили двумя заменами. Это решение Edward; сессия так не поступает молча.
6. **Только файлы, перечисленные в тикете.** Код, `.claude/` и Xcode-проект — никогда.
7. **Перекрёстные ссылки.** После применения проверить, что каждый упомянутый в «Стало» § существует в целевом документе.
8. **Пометка [Edward] в «Стало»** допустима, только если тикет указывает, где и когда принято решение.

### 2.2 Формат тикета-входящих **[штаб]**

```
Заголовок: docs: <что меняется> (<основание>)
Класс: trivial · Среда: облако
Основание: решение Edward <дата>, <где записано>
Файлы: <список>
Блоки: A1…An — «Было» / «Стало», каждый в блоке кода
Не трогать: <если есть>
```

## 3. Политика коммитов и сквоша

Решено **[Edward]**:
- автор коммитов — `edvard.froll@gmail.com`;
- без `Co-Authored-By`, без «Generated with/by», без ссылок на сессии.

Ловушка сквоша **[штаб]**: при squash merge GitHub сам добавляет `Co-authored-by` за каждого автора коммитов в PR, который отличается от того, кто мержит. Поэтому правило работает только в два слоя:
1. **Коммит:** каждая сессия коммитит сразу с автором `edvard.froll@gmail.com`. Что сессии используют по умолчанию — шаг 11 проверки коннектора (§8). Уже известно: облачная сессия Harness-0 закоммитила от `Claude <noreply@anthropic.com>` (PR #1), то есть по умолчанию автор неверный. Хук `commit-msg` отклоняет запрещённые трейлеры (§7).
2. **Репозиторий:** разрешён только squash merge; сообщение сквоша — заголовок PR (или заголовок + описание без трейлеров). Edward настраивает это в GitHub один раз.

Формат сообщения **[штаб]:** `MW-n: <imperative, English>`. Ветка: `MW-n-<slug>`. Исключение до появления тикетов — `harness-0:`.

## 6. Маршрутизация облако / Mac **[штаб]**

- **Облако:** docs, архитектура, критика, нарезка, ревью диффа, Jira. Код — только пакет, тестируемый на Linux, если архитектор его выделит (`roadmap.md` §4 п. 2).
- **Mac:** всё, что требует сборки, симулятора или тестов приложения.
- Среда — поле тикета. Сессия, которая получила тикет не своей среды, останавливается и пишет об этом в комментарий.
