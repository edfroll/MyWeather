## 3. Ветки, коммиты, PR **[Edward]**

### 3.1 Ветки

- `main` — всегда зелёный, показательный релиз. Ветка по умолчанию. Пишется только релизным PR из `develop`.
- `develop` — точка слияния. PR тикетов идут в `develop`, **squash**.
- Релиз `develop → main` — **merge commit**, не squash: иначе ветки разойдутся по истории.
- Ветка тикета: `MW-n`, без slug: Jira связана с GitHub (§3.4), описание несёт заголовок PR (решение Edward
  07.11.2026). Её создаёт исполнитель на Mac.
- Облачный тред сменить ветку не может: пушит в ветку, которую назначила ему платформа
  (`claude/project-thread-…`). Связь с Jira тогда держит ключ `MW-n` в заголовке PR и в сообщении коммита
  (GitHub for Atlassian связывает по ним, §3.4). Выявлено пилотом MW-11.
- Исправление после Rejected (§4.1) — новая ветка с суффиксом `-reject-fix`: на Mac `MW-n-reject-fix`
  (решение Edward 07.11.2026). Тикет в Jira тот же. Сообщение коммита — обычное `MW-n: …` (§3.2), суффикс только
  в имени ветки. Заголовок PR (он же сообщение сквоша) — `MW-n: <imperative> (reject-fix)`: ключ стоит в начале,
  формат §3.2 не ломается, а reject-fix находится в истории `develop`. Облачный тред, который не может назвать ветку,
  держит метку только в заголовке PR.

## 4. Jira **[Edward]**

### 4.1 Статусы

| Статус | id | Значит | Кто переводит |
|---|---|---|---|
| To Do | 10000 | готов к работе | координатор, Edward |
| In Progress | 10001 | тред взял тикет | тред тикета |
| Blocked | 10008 | ждёт решения или внешнего; комментарий с вопросом | любой тред |
| Code Review | 10003 | PR открыт; замечания чинятся в этом же PR, тикет колонку не покидает | тред тикета |
| Merged | 10009 | PR влит в `develop` | тред тикета (видит merge по подписке на PR) |
| Ready for Edward | 10010 | ждёт ручной проверки Edward; если в пачке есть изменения приложения — пора собрать билд `develop` (один на пачку) | координатор, пачкой (ниже), с уведомлением Edward |
| Verified | 10012 | Edward проверил | агент, по слову Edward |
| Rejected | 10011 | Edward забраковал; затем → To Do с комментарием, повторный цикл (ниже) | агент, по слову Edward |
| Done | 10002 | дошёл до `main` релизом | агент, после релиза |

**Правило доски — справа налево.** Чем правее колонка, тем важнее протолкнуть тикет. Сначала то, что застряло в
Code Review, затем Rejected, затем To Do. Внутри To Do следующий тикет — верхний по рангу (порядок карточек).
Поле Priority не используем.

**Пачка Merged → Ready for Edward** (решение Edward 07.11.2026). Колонка Ready for Edward — сигнал собрать Edward
билд для ручной проверки, а основной билд собирается один раз на весь спринт. Поэтому координатор переводит тикеты из Merged
не по одному, а **пачкой: все непроверенные тикеты спринта сразу, когда все они в Merged**. Так в билд точно
попадает весь спринт. Если в пачке нет изменений приложения (только harness, docs, CI), билд не собирается: Edward
проверяет тикеты по разделу «Проверка» их описания (§4.4).

**Тикет, добавленный после пачки.**
- Билд ещё не собран → тикет входит в пачку, билд ждёт его merge.
- Билд уже собран → тикет ждёт следующей пачки спринта (вместе с reject-fix, ниже). Если её не будет, отдельный
  билд под него — по решению Edward, иначе тикет переходит в следующий спринт.

**Исключение — тикет ревизии `architect-review-N` (§4.5 п. 3).** Он идёт в Ready for Edward один, сигнал «отчёт готов»;
merge и билда нет. Контрольный Chore по его находкам — отдельная пачка: с билдом, если меняет код приложения.

**После проверки.** Забракованные тикеты → Rejected → To Do и проходят конвейер своего класса заново (§5);
постановка фикса — комментарием в тикете со словами Edward о браке, ветка `-reject-fix` (§3.1). Остальные тикеты
пачки сразу → Verified. Когда все исправленные снова в Merged — так же пачкой в Ready for Edward и новый билд
`develop` с фиксами (если есть изменения приложения).

Переходы разрешены из любого статуса в любой; порядок держит эта таблица. Агент переводит тикет по id статуса:
название зависит от языка аккаунта.

### 4.2 Типы

Epic, Task, Bug, Chore. Chore — техдолг и рефакторинг; Bug — дефект. Chore и Bug из ревью, которые выходят за рамки
тикета, заводятся в бэклог; в спринт их ставит координатор. Кто и когда заводит — §6.4.

### 4.5 Спринт: неделя, объём как предел

1. Спринты Jira (фича Sprints в настройках проекта). Спринт недельный (решение Edward 07.11.2026: ход конвейера
   виден на доске). Дата конца — плановая: спринт закрывается не по дате, а по п. 4.
2. Верхний предел спринта — **5 тикетов класса standard/large или 10 тикетов любого класса**.
3. Когда все тикеты спринта в Verified, координатор ставит тикет ревизии (роль `mw-architect-review`). Summary
   тикета — `architect-review-N`, N — номер спринта; ключ — обычный `MW-n`. Ревизия одна на спринт (решение Edward 07.11.2026).
   Ревизия сверяет код с `docs/architecture.md`, поэтому начинается со спринта после прогона `mw-global-architect`
   и `mw-global-critic`; в Спринте 1 её нет.
   - ревизия чистая → Ready for Edward → Edward смотрит отчёт → Verified;
   - есть находки и Edward согласен → контрольный Chore в этот же спринт; Chore проходит весь путь до Verified,
     architect-review проверяет, что замечание закрыто → Verified.
   Релизный PR `develop → main` открывается, когда **все тикеты спринта и architect-review в Verified**. После merge
   релиза агент переводит их все, включая architect-review, в Done.
4. Спринт закрывается (Complete sprint) **только непосредственно перед стартом следующего**, в одном заходе со
   стартом (решение Edward 07.11.2026). После релиза спринт остаётся активным: доска показывает все его тикеты в Done —
   это сигнал Edward, что пора стартовать следующий. Когда Edward даёт старт, координатор (или тред по его поручению)
   закрывает текущий спринт и сразу стартует следующий. Закрытый спринт в Jira Cloud не переоткрыть, поэтому раньше
   времени `close` не вызывать.
5. Тикет в работе стоит в активном спринте (решение Edward 07.11.2026). Тред тикета при переводе в In Progress
   проверяет поле Sprint. Если тикета там нет и спринт не на пределе п. 2, тред добавляет его (`manageJiraSprint`,
   `addIssues`) и сообщает координатору; если на пределе — не добавляет и пишет координатору, решает он (§4.2).
   Исключение — окно между релизом и стартом следующего спринта (п. 4): если все тикеты активного спринта в Done, тред
   тикет в него не добавляет и пишет координатору. Координатор просит у Edward старт следующего спринта (закрыть
   текущий и стартовать следующий по п. 4) и кладёт тикет туда.

Спринтами управляет `manageJiraSprint` коннектора. Проверено 07.11.2026 на MW Спринт 1: `start` с датами, целью
и списком тикетов (тикеты переносятся в спринт); `createJiraIssue` с `assignToSprint` кладёт новый тикет в спринт.
`close` проверен 07.11.2026 при закрытии MW Спринт 1, `create` — при создании MW Спринт 2. ❓ `update` — при первой
надобности.

## 5. Классы и конвейер **[Edward]**

| Class | Этапы | Edward зовут |
|---|---|---|
| minor | исполнитель → ревью (круг 2) | аппрув PR |
| small | исполнитель → ревью (круг 2) | аппрув PR |
| standard | architect → critic → исполнитель → ревью (круги 1 и 2) | вопросы, требующие продуктового решения; аппрув PR |
| large | **research** → architect → critic → исполнитель → ревью (круги 1 и 2) | развилки архитектора; аппрув PR |

- Researcher можно вызвать в любом классе; для large он обязателен.
- В standard архитектор закрывает развилки очевидными ответами сам и зовёт Edward только за продуктовым решением.
- В minor и small архитектора нет: тред тикета сам ставит задачу исполнителю.
- Стопа «перед коммитом» нет. Точки Edward: развилки (large; продуктовые вопросы standard), аппрув PR, проверка на
  устройстве, релиз.

## 6. Ревью

### 6.1 Роли

| Роль | Где | Контекст |
|---|---|---|
| Архитектор тикета | тред тикета, живёт весь тикет | спека `docs/tasks/MW-n.md` с разделами «After review», «After review 2» |
| Критик | отдельный тред; тот же тред — на повторные проверки спеки | без контекста архитектора |
| Исполнитель | Remote Control на Mac, запускает тред тикета | спека + тикет |
| Ревьюер 1 (внутренний) | отдельный тред | дифф + спека |
| Ревьюер 2 (независимый) | новый тред без контекста | PR, `CLAUDE.md` и правила, на которые он ссылается; без спеки и тикета (§6.3) |

Треды открывает координатор по сообщению треда тикета. Замечания и ответы треды передают друг другу сами.

### 6.2 Круг 1 — внутренний (standard, large)

1. Исполнитель пушит ветку; тред тикета открывает **draft PR**; тикет → Code Review.
2. Ревьюер 1 отдаёт замечания архитектору. Архитектор принимает или оспаривает; спорят до общего списка: фиксим /
   ложные / вне скоупа (→ «Not included» в описании PR и Chore в бэклог).
3. Принятое → «After review» в спеке. Большие правки → критик проверяет спеку.
4. Исполнитель чинит; ревьюер 1 подтверждает.

### 6.3 Круг 2 — независимый (все классы)

1. PR → Ready for review; координатор открывает тред ревьюера 2 и передаёт его ссылку треду тикета (нужна для
   п. 5). Ревьюер оставляет треды в PR.
2. Архитектор (в minor/small — тред тикета) разбирает. Принятое → «After review 2» в спеке; большие правки → критик.
3. Исполнитель чинит без собственного ревью-прогона; архитектор отвечает в каждом треде PR.
4. Ревьюер 2 закрывает треды или добавляет новые. Все закрыты = аппрув Claude → уведомление Edward.
   Каждый комментарий в треде PR начинается с роли (`**[ревьюер 2]**`, `**[тред тикета]**`, `**[архитектор]**`).
   Перед resolve ревьюер пишет в треде `**[ревьюер 2]** снято`. Закрытый тред без такой строки последним
   комментарием ревьюера — нарушение (один логин, §1.2).
5. CI. Ревьюер читает дифф сразу, не дожидаясь CI. Последний тред закрывает только при зелёном CI на последнем
   коммите; CI идёт — ждёт сообщения треда тикета об окончании CI; CI красный — находка-блокер. Тред тикета
   (архитектор) сообщает ревьюеру 2, когда CI на последнем коммите закончился, с результатом.

Вход ревьюера 2 **[Edward, 05.11.2026]**: PR (описание, дифф, CI), `CLAUDE.md` и документы, на которые он ссылается
(`docs/engineering-principles.md`, этот документ, продукт и UX по нужному §). Спеку, тикет и тред тикета не читает:
смысл круга — взгляд без доводов архитектора, а не ревью без правил проекта.

### 6.4 Chore «вне скоупа» **[Edward, 05.11.2026]**

- Предложить вынести работу в Chore могут архитектор (в спеке), критик и оба ревьюера.
- Спека: архитектор предлагает Chore, критик и ревьюер 1 согласны → Chore заводится в бэклог без Edward.
- Круг 2: ревьюер 2 предлагает, архитектор (в minor/small — тред тикета) согласен → Chore заводится без Edward.
- Заводит тред, у которого сошлось согласие: архитектор или тред тикета. В описании PR — «Not included» со ссылкой
  на Chore.
- Edward зовут, если нужно его решение (продукт, развилка large) или роли не сошлись после обмена доводами.

## 7. Защита

### 7.1 Разрешения (`.claude/settings.json`)

Правила пишутся для обоих префиксов коннекторов: облако `mcp__<Server>__*`, Mac `mcp__claude_ai_<Server>__*` (ccm).

- **deny:** удаление и Confluence в Atlassian (`executeDestructive`, `createConfluenceContent`,
  `updateConfluenceContent`, `addGraphContext`); Gmail, Google Calendar, Google Drive целиком; опасный shell
  (`rm -rf`, `git push --force`, `git reset --hard`, `git clean`, `sudo`).
- **ask:** создание тикетов (`createJiraIssue`, `executeWrite`); `curl`, `wget`. В облаке (auto mode) не спросит —
  это защита на Mac.
- **allow:** чтение Atlassian, рутинные записи по своим тикетам (комментарий, переход, правка); конкретные команды
  shell для работы (git без опасных форм, `xcodebuild`, `xcrun simctl`, `swift`, `swiftlint`, `swiftformat`, чтение
  файлов).
- Общее разрешение `Bash` на Mac убирается (Edward, после merge этого документа).

### 7.2 Хуки (MW-10, 06.11.2026)

Хуки `PreToolUse` в `.claude/settings.json`, скрипты в `.claude/hooks/` (python3, только стандартная библиотека;
проверено на Linux, ❓ macOS — при первом запуске RC после merge MW-10). Блок — код выхода 2 с причиной, которую видит модель. Ошибка самого скрипта вызов **не** блокирует
(код 1, предупреждение): баг хука не должен останавливать конвейер.

| Хук | Срабатывает на | Пропускает |
|---|---|---|
| `jira_scope.py` | любой инструмент `mcp__*Atlassian*` (оба префикса §7.1) | `cloudId` — `7d0914d2-a05e-48d3-a0e5-46fe9e3870b9` или хост `myweather.atlassian.net`; ключи задач только `MW-n` (числовой id задачи не принимается); проект только `MW` (`project.key` или `project.id` `10000`); JQL — с `project = MW` (или `in (MW)`) либо с ключами `MW-n`, без других проектов и ключей, без `OR` на верхнем уровне (внутри скобок можно). Поля ищутся и во вложенных `inputs` у `execute*`. Вызовы без `cloudId` (`getAccessibleAtlassianResources`, `atlassianUserInfo`) проходят |
| `commit_guard.py` | `Bash` с `git commit` (в том числе за `env`, `command`, путём к git, внутри `bash -c`); трейлеры — и в `merge`, `cherry-pick`, `revert`, `tag`; GitHub MCP `push_files`, `create_or_update_file`, `delete_file`, `merge_pull_request` | автор коммита — только `168742523+edfroll@users.noreply.github.com` (`--author`, `GIT_AUTHOR_EMAIL=` в команде, `git -c user.email=`, иначе `git var GIT_AUTHOR_IDENT`; для `--amend` без `--reset-author` — автор исходного коммита); в сообщении нет `Co-Authored-By: Claude`, `Co-Authored-By: …noreply@anthropic.com`, `Claude-Session:`, «Generated with/by Claude Code», ссылок `claude.ai/code/session_`. Сообщение берётся из текста команды (`-m`, heredoc) и из файла `-F` |

- Тесты: `python3 .claude/hooks/tests/test_hooks.py` — подают хукам JSON так же, как Claude Code, и проверяют
  код выхода. Правка хука — вместе с тестом.
- Ложное срабатывание: в JQL текст вида `UTF-8` читается как ключ задачи чужого проекта — переписать запрос.
  Команда, где `git commit` соседствует с текстом про трейлеры (например, `grep` по ним), блокируется целиком —
  разнести по разным вызовам. JQL `key = MW-1 OR key = MW-2` блокируется — писать `key in (MW-1, MW-2)`.
- Граница — защита от случайности, не от намеренного обхода: сообщение коммита из редактора или из файла, созданного
  в той же команде, хук не видит. Главная граница Jira — сайт: на `myweather` сейчас один проект.
- **Где хуки действуют.** Claude Code читает хуки при старте сессии и правку `settings.json` в идущей сессии не
  подхватывает (проверено 06.11.2026 в треде MW-10). Облачный тред стартует на клоне `main` (§1.2), поэтому хуки
  из `develop` доходят до облачных тредов только с релизом. ❓ На Mac (Remote Control) хуки, по той же логике, действуют
  с ветки, на которой стартовала сессия — проверить при первом запуске RC после merge MW-10. Что хуки репо срабатывают в Claude Code на Linux, проверено 06.11.2026 headless-запуском
  `claude -p` в облачном контейнере: коммит с трейлером заблокирован, чистый прошёл.
