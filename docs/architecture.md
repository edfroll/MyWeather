## 1. Границы модулей и зависимости

```
                 ┌────────────────────────────── MyWeather (app target) ───────────────────────────────┐
                 │ вью, ViewModel, маппинг домен → серии графика, роза ветров, график осадков, роутинг │
                 └───────────────┬──────────────────────────────────────────────┬──────────────────────┘
                                 │                                              │
            ┌────────── ChartKit (package) ──────────┐          ┌────────── WeatherCore (package) ──────────┐
            │  ChartKit (SwiftUI + Charts)           │          │  WeatherCore                               │
            │        │                               │          │  домен, клиент Open-Meteo, сборка рядов,   │
            │        ▼                               │          │  кэш (SwiftData), локация (CoreLocation),  │
            │  ChartKitCore (только Foundation)      │          │  агрегации, единицы                        │
            └────────────────────────────────────────┘          └────────────────────────────────────────────┘
```

### A-1. Три модуля: приложение, `ChartKit`, `WeatherCore`
**Решение:** код делится на таргет приложения и два локальных SPM-пакета в `Packages/`:
`ChartKit` (таргеты `ChartKitCore` и `ChartKit`) и `WeatherCore` (один таргет). Приложение — единственный
интегратор: только оно видит оба пакета.
**Почему не:** всё кроме графиков в таргете приложения — изоляция акцентов №2 и №3 держалась бы на дисциплине;
мелкие пакеты (`Networking`, `Persistence`, `Location`…) — ширина без глубины, продукт §1;
имя `WeatherKit` — занято фреймворком Apple.
**Основание:** продукт §1, §1.1, §3.2 (модель и форматтеры не в таргете приложения); research §1.1 п. 3, §6, §7 №5.
**Как проверяется:** компилятор — `import` типа из чужого модуля без зависимости в `Package.swift` не собирается;
ревью — `Package.swift` обоих пакетов не содержит зависимостей, кроме указанных в A-2.
**Пометка:** [Edward] (E1)

### A-2. Граф зависимостей
**Решение:**
- `ChartKitCore` → только Foundation. Без `SwiftUI`, `Charts`, `CoreGraphics`, `UIKit`; геометрия — `Double`.
- `ChartKit` → `ChartKitCore`, `SwiftUI`, `Charts`. Реэкспорта нет: потребитель импортирует `ChartKit` и
  `ChartKitCore` явно.
- `WeatherCore` → Foundation, SwiftData, CoreLocation, MapKit (только обратный геокодинг, A-27). **Не зависит от
  `ChartKit`**: про графики не знает.
- Приложение → `ChartKit`, `WeatherCore`.
- `ChartKit` и `WeatherCore` друг о друге не знают. Типы домена превращаются в серии графика в приложении (A-46).
**Почему не:** `WeatherCore` → `ChartKitCore` ради сборки серий «в пакете с тестами» — связывает слой данных с
формой графика, а маппинг тривиален (структура в структуру), его логика (агрегации, единицы) и так в `WeatherCore`.
**Основание:** research §6 («`ChartKit` не знает слова погода»); продукт §1 (изоляция доказывается компилятором).
**Как проверяется:** компилятор; ревью `Package.swift`. CI-job на Linux (A-41) доказывает, что `ChartKitCore`
не тянет Apple-фреймворки.
**Пометка:** [сам: следствие A-1]

### A-3. Внутреннее деление `ChartKit` на `ChartKitCore` и `ChartKit`
**Решение:** в `ChartKitCore` — модели (A-5), нормализация и группы осей (A-6), деления (A-7), интерполяция и бинарный
поиск (A-13), вьюпорт как чистая математика (A-9), окно и децимация (A-12), индекс данных (A-9). В `ChartKit` —
вью графика, жесты, crosshair, наблюдаемые модели (A-9, A-10, A-14…A-19).
**Почему не:** один таргет — тесты алгоритмов потащат SwiftUI и не соберутся на Linux; дальнейшее дробление
(модели отдельно от алгоритмов) — граница без пользы.
**Основание:** research §7 №5; roadmap §4 п. 2.
**Как проверяется:** компилятор (A-2); на `ubuntu-latest` пакет собирается без `ChartKit` и `ChartKitCoreTests` проходят (A-41).
**Пометка:** [Edward] (E1, E3)

## 2. Публичный контракт `ChartKit`

### 2.1 `ChartKitCore`

### A-4. Ключ серии — параметр обобщённого типа
**Решение:** все типы с сериями обобщены по `Key: Hashable & Sendable`. Приложение подставляет `enum Metric`
из `WeatherCore` (11 случаев, A-47). Строковых ключей нет нигде.
**Почему не:** перечисление внутри `ChartKit` — пришлось бы назвать метрики погоды в ядре; `AnyHashable` — теряется
проверка типа, по сути строковый ключ; позиционный ключ «ряд 1 / ряд 2» — привязывает ядро к правилу UX о двух рядах.
**Основание:** research §4.5, §7 №2, §8 п. 6.
**Цена:** обобщение протекает в вью графика и замыкание показания. Вью принимает ещё два `@ViewBuilder`-содержимых
(полоса над `gaps`, A-14, и значок у верхнего края, A-16), поэтому она — `ChartView<Key, GapContent: View,
MarkContent: View>`; `AnyView` внутри не используется, чтобы не терять идентичность для анимаций (A-19). Приемлемо:
потребитель один (приложение), все три параметра выводятся из аргументов инициализатора.
**Как проверяется:** компилятор; ревью — нет `String`/`AnyHashable` в роли ключа серии.
**Пометка:** [сам: research §4.5 — типобезопасный ключ; перечисление в ядре невозможно по A-2]

### A-5. Модели данных графика
**Решение:** все модельные типы ядра — в `ChartKitCore`, все явно `Sendable` (у публичных типов Swift `Sendable`
не выводит), ограничение на ключ стоит на самих типах:
```swift
public struct ChartPoint: Sendable, Equatable { date: Date; value: Double? }      // nil — разрыв (под №9)
public struct ChartBand: Sendable, Equatable { date: Date; min, avg, max: Double; count: Int }
public struct ChartSegment<Element: Sendable>: Sendable { elements: [Element] }  // сегодня всегда один
public enum AxisSide: Sendable { case leading, trailing }
public struct LineSeries<Key: Hashable & Sendable>: Sendable { key: Key; side: AxisSide; segments: [ChartSegment<ChartPoint>] }
public struct BandSeries<Key: Hashable & Sendable>: Sendable { key: Key; side: AxisSide; segments: [ChartSegment<ChartBand>] }
public struct TopMark: Sendable, Hashable { date: Date; id: Int }                // содержимое значка — в UI (A-16)
public struct LineDecorations: Sendable { backgroundIntervals: [DateInterval]; topMarks: [TopMark] }
public struct DataGap: Sendable, Equatable { interval: DateInterval; kind: Kind } // Kind: .loading | .failed (A-14)
public enum ChartContent<Key: Hashable & Sendable>: Sendable {
    case lines([LineSeries<Key>], decorations: LineDecorations)   // ночь, значки — только у линий (A-16)
    case bands([BandSeries<Key>])
}
```
В UI-таргете `ChartKit` из этого остаётся только `@ViewBuilder`-содержимое значка и полосы над `gaps`.
Режим (линии / полосы) — это случай `ChartContent`, а не флаг: смешать линии и полосы на одном графике
невыразимо (P6). `ChartBand.count` — число исходных точек, нужно для взвешенной свёртки (A-12).
Ряд погоды равномерен и без дыр, поэтому сегмент всегда один, но форма `ChartSegment` и `ChartPoint.value: Double?`
остаётся в контракте.
**Почему не:** `mode`-флаг рядом с массивами — допускает полосы в «линейном» графике; убрать сегменты «пока не нужны» —
детект разрывов позже сломал бы публичную сигнатуру (research §8 п. 10); `LineDecorations` и `DataGap` в UI-таргете —
ядро не может на них сослаться (A-2), а `hasData(at:)` тестируется в `ChartKitCoreTests`.
**Основание:** research §1.1 п. 2, §3 №13, §3.1 («что всё-таки надо заложить под №9»), §5; engineering P6.
**Как проверяется:** компилятор — `ChartContent` передаётся в `@concurrent`-функцию построения индекса (A-38);
ревью — появление детекта разрывов не меняет публичных типов.
**Пометка:** [сам: research §3.1]

### A-6. Нормализация и оси: сторона вместо `axisGroupKey`
**Решение:** серии одной стороны (`AxisSide`) делят один масштаб; каждая сторона нормализуется в 0…1 отдельно
(механизм №1). Строкового `axisGroupKey` нет: какие серии делят ось, решает приложение, назначая сторону
(UX §4.4: одна единица — обе на левой). Паддинг 15 % и «кап» (механизм №2) задаются на сторону:
`AxisOptions(upperCap: Double?, headroom: Double)` — приложение передаёт `upperCap: 100` для процентов.
Денормализация подписей — функция ядра `AxisScale.value(atNormalized:)`; подписи делений форматирует приложение
замыканием (единицы — не дело ядра, research §5).
**Почему не:** перенести `axisGroupKey` как в исходнике — строковый ключ и неявная связь по индексу
(research §4.7 п. 4, 5); единый масштаб на все серии — ломает две оси.
**Основание:** research §3 №1, №2, §4.7; UX §4.4.
**Как проверяется:** тест `ChartKitCoreTests` — нормализация/денормализация обратимы, кап 100 соблюдается,
две серии на одной стороне получают общий масштаб.
**Пометка:** [сам: UX §4.4 уже задаёт стороны рядами]

### A-7. Деления осей
**Решение:** чистые функции ядра. Y — шаг из `[1, 2, 5, 10, 20, 25, 50] × 10ⁿ`, не больше 5 делений, считается
в единицах показа (значения приходят уже сконвертированными, A-46). X — шаг из ряда интервалов
(1 ч…12 ч, 1 д, 1 нед, 1 мес, 3 мес, 1 г), выравнивание по границам в `Calendar` графика (A-8),
плотность — от ширины в pt, переданной вью.
**Почему не:** штатные деления Swift Charts — на нормализованной шкале 0…1 они бессмысленны; деления в СИ с
пересчётом подписи — дают «3,3 °F»-шаги.
**Основание:** research §3 №10; UX S1 (деления каждые 3/6 ч по ширине).
**Как проверяется:** тест — шаг из списка, ≤ 5 делений, X-деления совпадают с полуночью локации в чужом поясе.
**Пометка:** [сам: research №10]

### A-8. Время в контракте: обязательный `Calendar`
**Решение:** конфигурация графика содержит `calendar: Calendar` без значения по умолчанию; его `timeZone` — пояс
локации, `firstWeekday` — из локали пользователя. Ядро использует его для делений X, границ суток и выравнивания
окна. Формат подписей X — замыкание приложения `(Date, XAxisGranularity) -> String`; по умолчанию его нет, чтобы
забытый пояс не мог подставиться из устройства.
**Почему не:** голый `TimeZone` — неделя и первый день недели живут в календаре (виды «Осадки», UX п. 6);
форматирование целиком снаружи без календаря в ядре — деления X нельзя выровнять по суткам локации.
**Основание:** продукт §2.5; research §5, §7 №7, §8 п. 11; UX §9 п. 14, 27.
**Как проверяется:** компилятор (нет дефолта); тест — для `Asia/Tokyo` при поясе устройства `Europe/Moscow`
деление «00:00» ложится на токийскую полночь.
**Пометка:** [сам: research §7 №7 — выбран вариант «параметр конфигурации», дополнен календарём]

### A-9. Разделение `ChartHelper`: индекс, вьюпорт, crosshair
**Решение:** три типа с разными жизненными циклами.

| Тип | Модуль | Что | Когда меняется | Наблюдаемость |
|---|---|---|---|---|
| `ChartDataIndex<Key>` | Core | масштабы сторон, отсортированные точки, якоря полос, префиксные суммы и счётчики значений; **одно** представление данных | при смене данных | неизменяемое значение, `Sendable` |
| `Viewport` | Core | `fullDomain`, `visible`, `minSpan`, `maxSpan`; pan, zoom, clamp — чистые функции | при жесте | значение |
| `ChartViewportModel` | UI | хранит `Viewport`; наблюдаемо только `visible`; поля жеста `@ObservationIgnored` | при жесте | `@Observable`, `@MainActor` |
| `CrosshairModel<Key>` | UI | текущее показание под пальцем | каждый кадр жеста | отдельный маленький `@Observable` |

`ChartDataIndex` строится детерминированной функцией от `ChartContent` и календаря, один раз, вне вью
(в ViewModel, A-43), а не в `.onAppear`/`.onChange`. **Вьюпортом владеет ViewModel страницы** и передаёт его в вью:
так сброс по событиям (UX §9 п. 20, 23) делается снаружи вызовом `reset()`, а приход данных окно не трогает.
`CrosshairModel` создаётся вью графика (`@State`) и наружу отдаёт показание через замыкание (A-15).
**Почему не:** один `@Observable`-класс — переход «пометить класс и забыть» перерисовывает весь `Chart` на каждый кадр
жеста (research §4.1); вьюпорт во `@State` вью — внешний сброс потребовал бы токена-триггера; два представления
данных как в исходнике — дефект research §4.7 п. 2.
**Основание:** research §4.1–4.4, §7 №1, §8 п. 3.
**Как проверяется:** тест — pan/zoom/clamp на `Viewport`; ревью — все поля жеста `@ObservationIgnored`, вью графика
не считает индекс; на устройстве — Instruments: тело `Chart` не пересчитывается во время crosshair.
**Пометка:** [сам: research §7 №1]

### 2.2 `ChartKit` (SwiftUI)

### A-10. Жесты и отмена украденного жеста
**Решение:** переносятся три режима (`idle / panning / detailing`) и приём с `@GestureState` (механизмы №3, №4):
по сбросу `@GestureState` вызывается отмена активного жеста, если `onEnded` не пришёл. Режим — `enum`, поля жеста —
в ассоциированных значениях, а не набором опционалов (P6). Pan/zoom можно выключить конфигурацией: у «10 дней» их
нет (продукт §4.2). Пределы зума — `minSpan`/`maxSpan` (UX S1, S4).
**Почему не:** без `@GestureState` — залипание состояния, за которое в исходнике уже заплачено (research §8 п. 7).
**Основание:** research §3 №3, №4; продукт §4.2.
**Как проверяется:** тест — переходы режимов на чистой функции; на устройстве — жест, перехваченный скроллом,
не оставляет crosshair.
**Пометка:** [сам: research №3, №4]

### A-11. Приоритет жестов: пейджер → вертикальный скролл → график
**Решение:** pan графика — `DragGesture(minimumDistance:)` с решением по направлению первого смещения: горизонтальное —
график забирает жест (`highPriorityGesture`), вертикальное — отдаёт скроллу. Карточка осадков и ряды чипсов — нативные
горизонтальные `ScrollView`, они перехватывают горизонталь сами. Пейджер — `TabView(.page)` (iOS 17).
Если на iOS 17 горизонтальный `highPriorityGesture` внутри страницы `TabView` не блокирует перелистывание
(известная зона риска SwiftUI), фолбэк — пейджер на `ScrollView(.horizontal)` + `scrollTargetBehavior(.paging)`
(iOS 17) с `scrollDisabled` на время жеста графика. Выбор между ними — по прототипу, до первой фичи с графиком.
**Почему не:** `UIGestureRecognizerRepresentable` — iOS 18, только за `#available`, а нужен и на 17;
UIKit-пейджер — уход от SwiftUI ради одного места.
**Основание:** UX §2.3, §9 п. 3; research §3 №4.
**Как проверяется:** прототип на устройстве (iOS 17 и текущая) — §12 риск 1; ревью — вложенность трёх уровней
не ломает отмену украденного жеста (A-10).
**Пометка:** [сам: открыт до прототипа, §12]

### A-12. Оконный рендер и децимация
**Решение:** рисуются точки видимого домена ± 50 % (№7). Внутри окна — децимация min/max по бакетам с сохранением
хронологического порядка (№8). Для полос — своя свёртка бакета: `min` из минимумов, `max` из максимумов,
`avg = Σ(avgᵢ·countᵢ) / Σcountᵢ`, `count = Σcountᵢ`. Плотность — от `@Environment(\.displayScale)`, во время жеста
падает до 1 (приём `+Windowing.swift:61`). Децимация — чистая функция `ChartKitCore`, вызывается при отрисовке.
**Почему не:** простое среднее средних — смещает неравные крайние бакеты, а точность стоит одну строку
(research §7 №6); «каждое N-е» — съедает пики, ради которых смотрят пять лет; `UIScreen.main.scale` — deprecated.
**Основание:** продукт §2.3; research §3 №7, №8, §3.1, §4.6, §7 №6, §8 п. 8.
**Как проверяется:** тест — экстремумы сохраняются, порядок хронологический, взвешенное среднее на неравных бакетах;
на устройстве — пять лет по двум метрикам листается плавно (research §8 п. 8).
**Пометка:** [сам: research §7 №6 — взвешенное]

### A-13. Интерполяция и бинарный поиск
**Решение:** один `firstIndex(onOrAfter:)` по отсортированному массиву (№6) для интерполяции и нарезки окна.
На линиях значение под пальцем интерполируется линейно (№5), на полосах — ближайший якорь.
**Почему не:** поиск ближайшего перебором — O(n) на кадр на пяти годах.
**Основание:** research §3 №5, №6.
**Как проверяется:** тест — граничные случаи (до первой, после последней, точное попадание, `nil`-значения).
**Пометка:** [сам: research №5, №6]

### A-14. Частичные данные и «честный объём»
**Решение:** у графика два домена: **ось** (`fullDomain`) и **данные**. Конфигурация принимает
`gaps: [DataGap]` (тип ядра, A-5). Ядро:
- рисует ось на весь `fullDomain` сразу;
- над `gaps` рисует полосу, вид которой даёт приложение (`@ViewBuilder (DataGap) -> some View`, там же «↻»);
- считает «под пальцем есть данные» как «палец внутри домена серий и вне `gaps`», скрывает crosshair целиком, когда
  данных нет, и вызывает `onDataPresenceChange(Bool)` на каждой смене (приложение даёт haptic `selection`);
- пустой хвост после текущего часа — то же «нет данных»: домен оси до конца суток, ряд до текущего часа;
- сегмент из одной точки рисуется `PointMark`, а не пропадает.
Детект разрывов (№9) не переносится: нужен только признак «нет данных» и событие его смены.
**Почему не:** блокирующий индикатор — UX §6.3 [Edward] требует прогрессивной отрисовки; ядро, требующее полного ряда,
не умеет показать кэшированную часть сразу (продукт §6.6).
**Основание:** UX §4.3, §6.3, §9 п. 2, п. 29, «Уточнения к продукту» (честный объём); research §7 №8.
**Как проверяется:** тест — `hasData(at:)` на краях `gaps` и хвоста; на устройстве — haptic на границе в обе стороны.
**Пометка:** [сам: ложится на ядро, возврата в UX нет]

### A-15. Показание над графиком вместо плавающего тултипа
**Решение:** ядро не рисует тултип. Оно отдаёт показание `CrosshairReading<Key>`
(дата + по каждой серии значение или тройка min/avg/max + сторона) через замыкание `onReadingChange`.
Приложение показывает его в шапке карточки вместо заголовка (UX §4.3). Раскладку «одна строка или серия ряда 2
строкой ниже» выбирает `ViewThatFits` (iOS 16) по реальной ширине содержимого — размер измеряется, а не
задаётся числом. Механизм удержания тултипа в границах (№11) не переносится. Внутри графика ядро рисует только
вертикальную линию и точки-маркеры (№12: на полосах три точки).
**Почему не:** перенести тултип с формулой высоты — магические числа (research §4.7 п. 3) и перекрытие точек на
320 pt (UX §4.3); измерять через `GeometryReader` + `PreferenceKey` вручную — `ViewThatFits` решает ровно эту задачу.
**Основание:** UX §4.3, §9 п. 4; продукт §4.2; research §3 №11, №12, §7.1 №6, §8 п. 9.
**Как проверяется:** ревью — в ядре нет констант высоты показания; на устройстве — ru ↔ en и мм рт. ст. на 320 pt
не ломают раскладку.
**Пометка:** [сам: UX §9 п. 4]

### A-16. Фоновые интервалы и значки у верхнего края
**Решение:** `LineDecorations(backgroundIntervals: [DateInterval], topMarks: [TopMark])` — типы ядра (A-5),
а содержимое значка — `@ViewBuilder` приложения в UI-таргете. Существуют только в случае `.lines` (A-5): у полос ночи нет
по построению. Что такое ночь, ядро не знает: интервалы считает приложение из восхода и заката (A-24).
**Почему не:** интервалы в общей конфигурации — их можно было бы передать полосам вопреки UX §4.6.
**Основание:** UX §7.3, §9 п. 12; research §5; продукт §3.1.
**Как проверяется:** компилятор (у `.bands` нет поля); ревью.
**Пометка:** [сам: UX п. 12]

### A-17. Маркеры аномалий
**Решение:** у серии необязательный `threshold: Double?` в единицах показа и стиль маркера из приложения.
Линии: точки-маркеры на значениях ≥ порога поверх линии. Полосы: маркер на границе максимума, если `max ≥ порог`.
Порог задаётся в СИ (15 м/с) в приложении и конвертируется вместе с рядом (A-46).
**Почему не:** перекраска самой линии — UX §7.4 требует линию цвета ряда.
**Основание:** продукт §4.3; UX §7.4, §9 п. 11.
**Как проверяется:** тест — отбор точек ≥ порога в окне; ревью — порог и цвет не захардкожены в ядре.
**Пометка:** [сам: UX п. 11]

### A-18. Стиль серий, строки и ресурсы
**Решение:** цвет и пунктир серии — `SeriesStyle`, передаётся приложением вместе с серией; цвет задаётся **рядом**,
а не метрикой (таблицы «метрика → цвет» нет). Строк на языке пользователя и обращений к Assets в `ChartKit` нет;
форматтеры — только с локалью окружения.
**Почему не:** `DesignSystem`-цвета в ядре — research §4.6.
**Основание:** UX §7.2, §9 п. 18; research §4.6, §8 п. 2.
**Как проверяется:** ревью — `grep` по `ChartKit` на `Color(` с литералами, `"…"` в `Text`, `Locale(identifier:`.
**Пометка:** [вводные UX §7.2]

### A-19. Анимации без `.id()`
**Решение:** смена линий на полосы — кросс-фейд ~0,25 с переходом между двумя ветками `ChartContent`
(`.transition(.opacity)` по случаю перечисления); появление ряда 2 — анимация вставки серии с устойчивой
идентичностью по `Key`. `.id()` на графике не используется.
**Почему не:** `.id(chartId)` пересоздаёт `Chart` и теряет анимацию (research §4.7 п. 6).
**Основание:** UX §4.5, §9 п. 13.
**Как проверяется:** ревью; на устройстве — кросс-фейд виден при смене диапазона 7 д ↔ 30 д.

## 3. Данные и сеть

### A-20. Клиент Open-Meteo и граница данных
**Решение:** в `WeatherCore` — `OpenMeteoClient` (`struct`, `Sendable`) поверх протокола
`HTTPTransport { func data(for: URLRequest) async throws -> (Data, HTTPURLResponse) }`. В приложении транспорт —
`URLSession`, в тестах — фикстуры (A-42). Ответ декодируется в DTO и **сразу** превращается в доменные типы
(`HourlyGrid`, A-22); дальше DTO не ходят (P7). `null` в ответе — `Float.nan` в хранении, `nil` в домене.
Ошибки — `enum WeatherError` (сеть, лимит 429, разбор, нет данных), без `String`-сообщений.
**Почему не:** репозиторий, ходящий в `URLSession` напрямую, — тесты пошли бы в сеть (API §5 п. 2).
**Основание:** research §1 (URLSession + async/await); API §5; roadmap §4 п. 5; P7.
**Как проверяется:** тест на фикстурах; ревью — `URLSession` упоминается только в приложении.
**Пометка:** [сам: roadmap §4 п. 5]

### A-21. Обязательные параметры и состав запросов
**Решение:** каждый запрос несёт `timezone=auto`, `wind_speed_unit=ms`, `timeformat=unixtime`; других параметров
единиц нет.

| Запрос | Хост | Параметры | Переменные |
|---|---|---|---|
| Прогноз | Forecast | `forecast_days=16`, `models` не передаётся (`best_match`), без `past_days`, без `current` | hourly: 11 метрик + `weather_code`, `is_day`; daily: `weather_code`, `sunrise`, `sunset`, `temperature_2m_max`, `temperature_2m_min` |
| Архив | Archive | `models=ecmwf_ifs`, `start_date`/`end_date` | hourly: 9 метрик (без `uv_index`, `precipitation_probability`); daily: `sunrise`, `sunset` |
| УФ истории | Historical Forecast | `start_date`/`end_date` | hourly: `uv_index` |
| Поиск города | Geocoding | `name`, `language` (ru/en по языку приложения), `count` | — |

`weather_code` и `is_day` в истории не запрашиваются: исторические экраны их не показывают.
**Почему не:** `past_days` — ряд надёжен ~55 дней (OM-1); `current` — UX §6.2 [Edward]; `models=ecmwf_ifs` у
прогноза — A-25.
**Основание:** продукт §2.1, §2.2, §2.4, §7.1; API §2, §3; UX §6.2.
**Как проверяется:** тест — сборка URL по каждому запросу сравнивается с эталоном.
**Пометка:** [вводные продукт §2.1, §7.1; API §2]

### A-22. Время: UTC-сетка плюс пояс локации
**Решение:** ряд в домене — `HourlyGrid(start: Date, count: Int, values: [Metric: [Float]])`: начало — абсолютный
момент из `unixtime`, шаг — 3600 с, метки не хранятся (продукт §6.2). Пояс локации — `TimeZone` из поля
`timezone` ответа, хранится у локации. Сетка не обязана начинаться на целом часе UTC (пояса с `+05:30`). Всё, что
режет время на сутки, недели и месяцы, работает через `Calendar` с поясом локации (A-8, A-48).
Запросы с датами (`start_date`/`end_date` — местные сутки) делаются с запасом в одни сутки на **краях плана**
догрузки (A-32), а не у каждого куска: внутренние стыки кусков смежны, запас там не нужен. Ответ обрезается до нужных
моментов: запас почти бесплатен, вес считается по двум неделям (API §5). Правая граница зависит от источника:
- **Archive** — `min(конец + 1 сутки, сегодня локации, сегодня UTC)`. Archive считает «текущую дату» по UTC и отвечает
  400 на `end_date` позже неё, хотя сами даты запроса — местные (API §6 п. 2, п. 9). Западнее UTC граница — сегодня
  локации, восточнее — сегодня UTC: в Окленде (UTC+13) до 13:00 местного времени местное «сегодня» в Archive не
  запрашивается.
- **Historical Forecast** — `min(конец + 1 сутки, сегодня локации)`: ограничения по UTC у него нет (API §6 п. 9).

Если после обрезки `start_date` позже `end_date`, запрос к источнику не отправляется: кусок пуст, а не ошибка.
Следствие для поясов восточнее UTC: прошедшие часы местного «сегодня», пока в UTC ещё вчера, в Archive отсутствуют и
идут как `gaps` архивных метрик (A-23). Из Historical Forecast они не добираются: линия не склеивается из двух моделей
(A-25). Часы появляются при следующем обновлении хвоста после смены суток UTC (A-30, A-35).
**Почему не:** хранить местные метки из `timezone=auto` как есть — смещение `utc_offset_seconds` одно на ответ,
и при переходе на летнее время сетка в местном времени сдвинется на час; запрос без `timezone` — продукт §2.5
требует `auto`, и `daily` без него не работает (API §2).
**Основание:** продукт §2.5, §6.2; API §2, §6 п. 2, 8, 9; research §5 («часовой пояс локации»).
**Как проверяется:** тест на фикстурах Берлина и Нью-Йорка через переход на летнее время: сутки 23 и 25 часов
агрегируются верно; тест сборки URL с подменным `now` — `end_date` Archive не позже сегодня локации и сегодня UTC
(Окленд, 13.11 06:24 NZDT = 12.11 UTC: `end_date` Archive = 12.11, фикстура `archive-auckland-end-today` — 400 на 13.11),
`end_date` Historical Forecast — сегодня локации (13.11); пустой после обрезки кусок не даёт запроса.
`timeformat=unixtime` с `timezone=auto` отдаёт абсолютные UTC-секунды — сверено (API §6 п. 8, MW-32).
**Пометка:** [сам: продукт §2.5 и §6.2 вместе, расхождение R7]

### A-23. Шов истории: Archive + Historical Forecast
**Решение:** `HistoryAssembler` (чистая функция `WeatherCore`) склеивает 9 метрик Archive и `uv_index` Historical
Forecast в одну `HourlyGrid` по моменту времени. Источники лежат отдельными чанками со своим покрытием (A-28, A-32):
после S1 архив за неделю есть, а УФ за неё ещё нет. Поэтому склейка — по моменту: общая сетка — объединение моментов
источников на шаге 3600 с, час, которого нет в источнике, — `nil` у его метрик; `gaps` результата — объединение
недостающих интервалов источников, каждый помечен своими метриками. Момент, не лежащий на общем шаге (сдвиг сетки
источника не на целый час), — ошибка разбора, а не тихий сдвиг. История обрезается по текущему часу локации: будущих часов в ней нет, хотя API их отдаёт.
Восточнее UTC архив может кончаться раньше текущего часа (граница по UTC, A-22): недостающие часы до текущего —
`gaps` архивных метрик, `uv_index` за них может быть.
`precipitation_probability` в истории отсутствует (OM-2): чип скрыт (A-47).
**Почему не:** склейка по индексу массива — дубль или пропуск часа на стыке (research §3.1).
**Основание:** продукт §2.1, §2.4 п. 1; API §6 п. 2, OM-2; research §3.1 («шов прогноз/архив»).
**Как проверяется:** тест — стык без дубля и пропуска; архив есть, а УФ нет на части диапазона — `nil` и `gaps` только у
`uv_index`; сдвиг сетки не на целый час — ошибка; обрезка по текущему часу в поясе локации; архив Окленда кончается
на местной полуночи 13.11, текущий час — 06:00: часы от полуночи до текущего — в `gaps` архивных метрик.
**Пометка:** [вводные продукт §2.4]

### A-24. Восход, закат, ночь
**Решение:** восход и закат — из `daily` того же источника, что и график (прогноз — Forecast, история ≤ 7 дней —
Archive). Интервалы ночи и значки (A-16) строит приложение из этих моментов. Под полярным днём и ночью (`sunrise` нет)
интервалов нет или все сутки — ночь, по `is_day` прогноза; для истории — без затенения.
**Почему не:** считать солнце формулой — лишний код при данных в ответе.
**Основание:** продукт §3.1 («Сутки на графике»); UX §7.3, §9 п. 12.
**Как проверяется:** тест на фикстуре с полярным днём (Мурманск, июнь).
**Пометка:** [сам]

### A-25. Одна серия или один столбец — одна модель
**Решение:** Forecast запрашивается с `best_match`. Инвариант: **точка или столбец графика берётся из одной модели,
линия или полоса не склеивается из двух**. Почасовой график, «10 дней», ветер и «Текущая погода» на главном — только
Forecast, включая прошедшие часы сегодня (UX §6.2); история — только Archive + Historical Forecast до текущего часа.
Единственный экран с двумя источниками — карточка «Осадки» на S1 (UX S1: от −7 до +10 дней [Edward]): столбцы
D−7…D−1 — суточные суммы `precipitation` из архива (`ecmwf_ifs`, через кэш архива, A-28…A-32), столбцы «сегодня» и
D+1…D+9 — из Forecast. Шов проходит между столбцами «вчера» и «сегодня», а не по линии: столбец — отдельная величина,
излома нет. Сборка этой серии — чистая функция `WeatherCore` (`precipitationStrip`), тест — на стыке нет дубля и
пропуска суток. Расхождение моделей (до 2,5 °C, API §6 п. 3) видно только между экранами.
**Почему не:** `models=ecmwf_ifs` у Forecast — хуже краткосрочный прогноз, чем у `best_match` с местными моделями,
а наличие `precipitation_probability` у детерминированной модели не проверено; склеивать линию на «сейчас» — излом
на графике; Forecast с `past_days=7` для осадков — противоречит продукту §2.1, §2.4 и OM-1 [Edward]; сузить карточку
до 0…+10 — меняет UX S1 [Edward].
**Основание:** продукт §2.4 п. 2 («решает архитектор»); UX S1 «Карточка „Осадки“»; API §6 п. 3, OM-1; research §7 №3.
**Как проверяется:** ревью — ни одна линия или полоса не строится из двух `HourlyGrid`; тест `precipitationStrip` —
стык «вчера / сегодня» без дубля и пропуска.
**Пометка:** [сам: продукт §2.4 п. 2; MW-23 K-1, вариант А]

### A-26. Бюджет вызовов
**Решение:**

| Операция | HTTP-запросов | Вес, вызовов (API §5) |
|---|---|---|
| Прогноз одной локации | 1 | ≈ 1,5 (16 суток, 13 hourly-переменных; вес `daily` — ❓) |
| Осадки D−7…D−1 на S1, первый показ локации | +1 (Archive, 9 метрик за 8 суток — тот же чанк, что у истории) | 1 |
| Хвост архива на S1 | +1 (Archive), вместе с прогнозом, если хвост старше часа (A-30) | 1 |
| Полная история одной локации, 5 лет | 10 (5 кусков Archive + 5 кусков Historical Forecast) | ≈ 260 (`daily` — ❓) |
| Хвост истории при входе в S4 | 2 (Archive + Historical Forecast) | 2 |
| Поиск города | 1 на запрос, с задержкой ввода 300 мс | — |

Единица нарезки — **кусок ≤ 366 суток вместе с запасом A-22**; запас стоит только на краях плана, поэтому пять лет
плюс сутки запаса слева (1 827 суток) ложатся в 5 кусков на API. Одинаковые запросы в полёте склеиваются (A-34). Кусков короче двух недель по своей воле не
бывает: соседние дыры объединяются (A-32). Тесты в сеть не ходят (A-42). Учитывается ли `daily` в весе, API §5 не
говорит; на вывод (≈ 2,6 % дневного лимита на полную историю) это не влияет.
**Почему не:** запрашивать историю месячными кусками — 60 HTTP-запросов вместо 10 при том же весе; осадки S1 только
одной переменной — тот же вызов, но чанк архива остался бы неполным и история перекачала бы его.
**Основание:** API §5; продукт §6.4; UX S1 «Осадки».
**Как проверяется:** тест — план догрузки для «30 д → 5 лет» даёт ≤ 10 запросов, каждый ≤ 366 суток; пять лет — ровно 5 кусков на API; ревью.
**Пометка:** [сам: API §5]

### A-27. Геокодинг: поиск и название геопозиции
**Решение:** поиск — Open-Meteo Geocoding (продукт §5). Название геопозиции — обратный геокодинг системы:
`MKReverseGeocodingRequest` под `#available(iOS 26, *)`, фолбэк — `CLGeocoder.reverseGeocodeLocation`
(deprecated с iOS 26, работает). Название кэшируется вместе с ключом локации (A-31); пока его нет, UI показывает
«Моё местоположение» (UX п. 9). Карта не используется: MapKit здесь только как сервис геокодинга.
**Почему не:** ближайший город из Geocoding-поиска по координатам — у Open-Meteo нет обратного поиска;
сторонний сервис — новый ключ API и лимиты.
**Основание:** UX §9 п. 9; API §6 п. 5; `CLAUDE.md` (`#available`).
**Как проверяется:** компилятор (`#available`); ревью; тест разбора Geocoding на фикстурах `geocoding-*`. Поля и язык
ответа сверены (API §6 п. 5, MW-32): `timezone` есть, `language=ru` переводит `name`, `country`, `admin1`; без
совпадений ответ — без ключа `results`, разбор даёт пустой список, а не ошибку.
**Пометка:** [сам: UX п. 9]

### A-28. Хранилище: SwiftData за одним актором, два файла
**Решение:** SwiftData, доступ только через `@ModelActor actor WeatherStore` в `WeatherCore` — единственный писатель
(P9). Один `ModelContainer` с **двумя `ModelConfiguration`, то есть двумя файлами хранилища**:

| Хранилище | Модели (эскиз полей) | Схема |
|---|---|---|
| Пользовательские данные | `StoredLocation`: `key`, имя, координаты, `timeZoneID`, `order`, `kind` (город / геопозиция), `lastAccess` | `VersionedSchema` с первой версии, изменения — через `SchemaMigrationPlan` |
| Кэш | `SeriesChunk`: `locationKey`, `source` (`.archive` / `.historicalUV` / `.forecast`), `start`, `hourCount`, `payload: Data` (упакованные `Float` по метрикам), `finalThrough: Date?`, `fetchedAt`, `lastAccess`, `byteCount`, `formatVersion`; `DailyChunk`: восход, закат по дням, для прогноза ещё `weather_code`, макс/мин температуры | без миграций: при несовпадении схемы файл кэша удаляется и наполняется из сети |

Источник — часть ключа чанка: архив (9 метрик + `daily`) и УФ из Historical Forecast лежат отдельными чанками, у каждого
своё покрытие (A-32). Так S1 берёт только архив, а история дозапрашивает УФ отдельно.
Через границу актора ходят только `Sendable`-снимки (`HourlyGrid`, структуры), не `@Model`-объекты.
`formatVersion` при несовпадении — чанк считается отсутствующим и перекачивается.
**Почему не:** одно хранилище — первая же правка полей кэша потребует миграции ради сохранения списка городов, а
удаление файла сотрёт список, который пользователь не восстановит; построчное хранение — ~79 000 записей на
локацию-год (продукт §6.2); файлы на диске рядом с SwiftData — два источника истины для LRU; `ModelContext` на главном
акторе — разбор пяти лет на главном потоке.
**Основание:** продукт §5 (ручной порядок), §6.2, §10 (SwiftData); research §1.1 п. 4; P9.
**Как проверяется:** компилятор (`@Model` не `Sendable`, не пересечёт актор); тест — запись и чтение чанка в
in-memory `ModelContainer`; тест — несовпадение схемы кэша удаляет кэш и не трогает `StoredLocation`; один контейнер с двумя конфигурациями и частичной `VersionedSchema` — §12 риск 6.
**Пометка:** [сам: продукт §6.2; MW-23 K-3]

### A-29. Единица хранения — чанк «локация × слой × месяц»
**Решение:** архив и УФ режутся на чанки по календарному месяцу в поясе локации (5 лет — 60 чанков на источник, архив
~30 КБ на чанк по 9 метрикам). Прогноз — один чанк на локацию, заменяется целиком при обновлении. Чанки независимы: догрузка,
финализация хвоста и LRU работают на уровне чанка.
**Почему не:** один блоб на локацию — переписывать 2 МБ ради суток хвоста; суточные чанки — 1 826 записей на
пять лет и медленная выборка.
**Основание:** продукт §6.2–6.4.
**Как проверяется:** тест — разрезание и сборка ряда через границу месяца и через переход на летнее время.
**Пометка:** [сам]

### A-30. Слои и уточняемый хвост
**Решение:**
- **Прогноз:** TTL 1 час от `fetchedAt`.
- **Хвост архива:** **последние трое суток локации (N = 3)**: сегодня, вчера, позавчера.
- **Окончательность — дата, а не флаг.** У чанка поле `finalThrough: Date?` — момент, до которого его данные
  бессрочны. При записи оно равно началу самых ранних суток, которым на момент `fetchedAt` было не больше N суток
  (обрезанному границами чанка); `nil` — окончательных часов нет, `finalThrough == конец чанка` — чанк бессрочен
  целиком. Покрытие для догрузки (A-32) — `[start, finalThrough)`: перекачивается только хвост, а не весь месяц.
  Сутки становятся бессрочными при первой загрузке, сделанной, когда им уже больше N суток. Повторная загрузка тех же
  часов в то же время даёт то же `finalThrough` (P10); «бессрочные сутки» выражены одной датой (P6).
- **Когда перекачивать хвост:** при входе в S4 — архив и УФ, 2 запроса; на S1 — только архив (осадки D−7…D−1, A-25),
  1 запрос вместе с обновлением прогноза. В обоих случаях — если хвост старше 1 часа (UX §4.6 в редакции §10 R1).
  Другого фонового обновления истории нет.
- **Архив за границей хвоста:** бессрочный, в сеть не ходит вовсе.

Основание — сравнение снимка 13.10.2026 21:32 UTC с данными 07.11.2026 (API §6 п. 1). Снимок снят в сутках GMT
(скрипт без `timezone`). У 4 городов в Archive (9 метрик) и Historical Forecast изменились только часы суток съёмки
по GMT: самый старый изменённый час — ~21,5 ч, самый молодой неизменный — ~22,5 ч на момент снимка. При N = 2
самые молодые окончательные часы были бы возрастом 24 ч, то есть запас всего 1,5–2,5 ч, а наблюдение одно и снято
в одно время суток относительно циклов IFS (раз в 6 ч, API §4). При N = 3 окончательным становится только то, чему не
меньше 48 ч, запас ~25 ч.
**Почему не:** N = 2 — запас 1,5–2,5 ч по одному наблюдению, а ошибка необратима: перезаписанный час навсегда остался
бы в «бессрочном» архиве и молча нарушил продукт §6.1; N больше 3 — без подтверждённой причины. Цена N = 3 та же, что
у N = 2: хвост — всегда те же 1–2 запроса, кусок короче двух недель стоит 1 вызов (API §5), разница — сутки байтов.
**Основание:** продукт §2.4 («оговорка про свежий хвост»), §6.1; API §4, §5, §6 п. 1–2; UX §4.6.
**Как проверяется:** тест — `finalThrough` на фиктивных часах: загрузка через 1 ч, 1 сут, 3 сут, 30 сут, повторная
загрузка того же диапазона; `fetchPlan` при входе в S4 запрашивает только хвост.
**Пометка:** [Edward] (E5: N — по сравнению снимка) + значение [сам: сравнение 07.11.2026; MW-23 K-4]

### A-31. Ключ локации
**Решение:** город — координаты из Geocoding как есть плюс его `id`. Геопозиция — координаты, огрублённые до 0,1°
(≈ сетка IFS 9 км): сдвиг на километр не перекачивает пять лет. **Гистерезис:** новая точка сохраняет текущий ключ
геопозиции, пока она внутри его ячейки 0,1° или не дальше 5 км за её границей; расстояние считается от границы
ячейки, а не от её центра (полуширина ячейки по широте ~5,5 км больше 5 км). Шум GPS у границы ключ не переключает. Уехал дальше —
новый ключ и новая история; прежняя уходит по LRU.
**Почему не:** точные координаты — UX п. 28; привязка к сетке источника из ответа API — ключ нужен до запроса, иначе
без сети не найти кэш; огрубление без гистерезиса — у границы ячейки ключ скачет от запуска к запуску.
**Основание:** UX §9 п. 28.
**Как проверяется:** тест — огрубление на границах ячейки и у отрицательных координат; точка в 1 км по другую
сторону границы сохраняет ключ, в 6 км — меняет.
**Пометка:** [сам: UX п. 28; MW-23 K-11]

### A-32. Догрузка только недостающего
**Решение:** чистая функция `fetchPlan(requested: DateInterval, covered: [ChunkCoverage], now:) -> [FetchRequest]`:
считается отдельно для каждого источника (`.archive`, `.historicalUV`, A-28): запрошенное минус покрытое

**Почему не:** перезапрашивать весь диапазон — продукт §6.4 и бюджет (API §5 п. 1).
**Основание:** продукт §6.4; API §5; UX §6.3.

### A-33. Лимит 100 МБ и LRU
**Решение:** `WeatherStore` хранит сумму `byteCount`. После записи, если сумма > 100 МБ, удаляются чанки архива локаций
с самым старым `lastAccess`, целыми локациями, пока сумма не станет ≤ 80 МБ. Видимая локация не удаляется никогда.
`StoredLocation` (список городов) не вытесняется — только данные. Первыми вытесняются чанки без `StoredLocation`
(предпросмотр S3 без «Добавить», A-34). `lastAccess` обновляется при чтении для экрана, не чаще раза в минуту на
локацию.
**Почему не:** вытеснять по чанкам — дыры посреди истории, которые потом догружаются кусками дороже.
**Основание:** продукт §6.3.
**Как проверяется:** тест — вытеснение на in-memory хранилище с искусственно малым лимитом.
**Пометка:** [вводные продукт §6.3]

### A-34. Репозиторий: склейка запросов и идемпотентность
**Решение:** `actor WeatherRepository` в `WeatherCore` — точка входа для ViewModel: `forecast(for:)`,
`history(for:range:) -> AsyncThrowingStream<HistoryProgress>` (части от новых к старым), `refreshTail(for:)`.
Внутри — словарь задач в полёте по ключу запроса: второй вызов ждёт первую задачу, а не шлёт дубль. Разбор ответа —
`@concurrent`-функция, которую актор ждёт через `await`: пока разбирается годовой ответ, актор свободен для соседних
запросов. Запись в кэш — после успешного разбора, целым чанком; падение посреди загрузки оставляет кэш в прежнем
согласованном состоянии (P10). Время — зависимость: репозиторий получает `now: @Sendable () -> Date` через
инициализатор, как и транспорт; TTL, хвост и «текущий час» считаются только от него.
Предпросмотр S3 идёт тем же путём: прогноз города кэшируется под его ключом (A-31) ещё до «Добавить». После «Добавить»
кэш переиспользуется; без «Добавить» чанки остаются без `StoredLocation` и вытесняются первыми (A-33).
**Почему не:** склейка на стороне ViewModel — у двух экранов одной локации (S1 и S2) были бы два запроса.
**Основание:** API §5; P9, P10; UX §4.6 (несколько триггеров обновления).
**Как проверяется:** тест — два параллельных вызова дают один запрос в фейковый транспорт; ошибка в середине — кэш
не тронут; TTL и хвост — на подставленном `now`.
**Пометка:** [сам]

### A-36. `LocationService`: делегат в `AsyncStream` + `liveUpdates`
**Решение:** в `WeatherCore`:
```swift
@MainActor public final class LocationService {
    public let authorization: AsyncStream<Authorization>      // из делегата; ровно один потребитель
    public func currentCoordinate() async throws -> Coordinate // первый CLLocationUpdate из liveUpdates()
}
```
- `CLLocationManager` создаётся и живёт на главном акторе: его колбэки приходят в run loop потока создания.
- Делегат — отдельный объект; его методы `nonisolated` и только кладут значение в `AsyncStream.Continuation`
  (`Sendable`), никакого общего изменяемого состояния. Поэтому не нужны ни `@preconcurrency`, ни
  `@unchecked Sendable`, ни `nonisolated(unsafe)` (P8).
- Координаты — `CLLocationUpdate.liveUpdates()` (iOS 17): берётся первое обновление с координатой, затем поток
  отменяется. Таймаут — `withThrowingTaskGroup` на 15 с.
- **У потока авторизации ровно один потребитель — `AppModel`** (корневая модель приложения, A-37). Она хранит
  текущий статус в `@Observable`-свойстве, и остальные (страница геопозиции, S2) читают его оттуда. Второй итератор
  `AsyncStream` не получил бы копию, значения делились бы между ними, поэтому раздачи потока нет: у состояния
  авторизации один владелец (P9), делегат пишет в единственный `Continuation`.
- Последние координаты сохраняются (A-37): без сети и без геолокации страница геопозиции показывает их кэш (UX §6.1).
Это показательный код акцента №2: комментарии в нём объясняют, почему делегат на главном акторе, почему методы
`nonisolated` и почему `Continuation` безопасно пересекает границу.
**Почему не:** всё через делегат (`requestLocation` + `CheckedContinuation`) — на iOS 17 для координат есть родной
async-API, а продолжение надо возобновить ровно один раз на каждом пути, включая ошибку и отмену; `actor`, владеющий
менеджером, — у исполнителя актора нет run loop, колбэки потеряются.
**Основание:** продукт §1.1 №2; research §1.1 п. 4.
**Как проверяется:** компилятор (Swift 6 strict, без глушителей); ревью — нет `@preconcurrency`, `@unchecked`,
`authorization` итерируется в одном месте (`AppModel`);
тест — маппинг `CLAuthorizationStatus` → `Authorization`; на устройстве — выдача и отзыв разрешения.
**Пометка:** [Edward] (E4)

## 6. Модель изоляции по слоям

### A-38. Настройки изоляции по таргетам
**Решение:**

| Таргет | Изоляция по умолчанию | Approachable Concurrency | Что вне главного актора |
|---|---|---|---|
| MyWeather (приложение) | `MainActor` | `YES` | ничего, кроме одной `@concurrent async`-функции построения `ChartDataIndex` |
| MyWeatherTests | `MainActor` | `YES` | — |
| `ChartKit` | `MainActor` | `YES` | — |
| `ChartKitCore` и тесты | `nonisolated` | `YES` | всё: чистые `Sendable`-значения и функции |
| `WeatherCore` и тесты | `nonisolated` | `YES` | `WeatherStore` (`@ModelActor`), `WeatherRepository` (`actor`), разбор и агрегации — через `HistoryAnalytics` (ниже); на главном только `LocationService` (A-36) |

Приложение и `ChartKit` — вью и ViewModel, им главный актор по умолчанию даёт `@MainActor` бесплатно (research §1.1
п. 1). Пакеты с данными и алгоритмами — `nonisolated` по умолчанию: репозиторий не может «тихо» оказаться на
главном акторе (research §1.1 п. 3), а уход с вызывающего актора пишется явно `@concurrent`, потому что при
Approachable Concurrency `nonisolated async` выполняется на исполнителе вызывающего. Тест-таргет повторяет настройки
своего модуля.

**Одна точка ухода тяжёлой работы с главного актора (P5).** `@concurrent` применим только к `async`-функциям, а
синхронная `nonisolated` функция, вызванная из ViewModel, выполнится на главном акторе. Поэтому:
- чистые функции разбора и агрегаций (A-20, A-49, A-51) — синхронные и с доступом `package`: их видят код и
  тесты пакета `WeatherCore`, но не приложение;
- конвертация единиц (A-46) остаётся `public` и синхронной: её вызывает маппер приложения на уже агрегированных рядах
  (≤ 1 826 точек на серию после A-49) или на почасовом прогнозе (≤ 384 ч, A-21), это не тяжёлая работа;
- приложению открыт только `public`-фасад `HistoryAnalytics` — `nonisolated struct` с `@concurrent async`-методами
  («суточные полосы за диапазон», «суммы осадков», «роза за диапазон»), которые вызывают синхронные функции под
  собой; разбор ответа — `@concurrent`-функция, её вызывает и ждёт только `WeatherRepository` (A-34);
- в приложении то же для `ChartDataIndex`: одна `@concurrent async`-функция построения индекса.
Так «агрегация пяти лет на главном потоке» не собирается: из ViewModel синхронную агрегацию просто не видно.

**Всё, что пересекает границу актора, — `Sendable`-значение, объявленное явно:** модели ядра (A-5), `HourlyGrid`,
`HistoryProgress` (A-34), `PageState` и `HistoryState` (A-35, A-53), `CrosshairReading<Key>` (A-15), `Authorization`.
Для публичных типов Swift `Sendable` не выводит, поэтому пометка стоит в объявлении.

В пакетах: `// swift-tools-version: 6.2` или новее, `swiftLanguageModes: [.v6]`, изоляция через
`swiftSettings` таргета: `.defaultIsolation(MainActor.self)` или `.defaultIsolation(nil)` и upcoming features
`NonisolatedNonsendingByDefault`, `InferIsolatedConformances` (Approachable Concurrency сверх языкового режима
Swift 6). Сверено под Swift 6.4 на Mac, MW-30 (§12 риск 5). Плюс `MemberImportVisibility`
в каждом таргете — [сам: паритет с приложением, MW-30 D-3].
**Почему не:** шаблон как есть (`MainActor` везде) — слой данных на главном потоке ловит только ревью;
`nonisolated` везде с ручным `@MainActor` — в таргете приложения нет кода вне главного актора, пометки были бы шумом.
**Основание:** roadmap §4 п. 1; research §1, §1.1; продукт §1.1 №2.
**Как проверяется:** компилятор — обращение к `WeatherStore` без `await` не собирается, а синхронные агрегации
(`package`) из приложения не видны; ревью `Package.swift`, build settings и фасада `HistoryAnalytics` — все его
`public`-методы `@concurrent async`. Тест на «не главный поток» не пишем:

### A-41. CI: тесты пакетов в обязательном check и Linux-job для `ChartKitCore`
**Решение:**
- **macOS-job `test`** (обязательный check в rulesets) дополняется шагами `swift test --package-path
  Packages/WeatherCore` и `swift test --package-path Packages/ChartKit`. Сейчас он отбирает
  `-only-testing:MyWeatherTests`, и тесты пакетов в схему приложения не входят; без этих шагов акцент №3 (кэш,
  хвост, шов, догрузка) в CI не проверялся бы вовсе.
- **Linux-job** `ubuntu-latest`: `swift test --package-path Packages/ChartKit`. `swift test` собирает все таргеты
  пакета, а `--filter` отбирает только запуск, поэтому граница задаётся в манифесте: таргет `ChartKit` (SwiftUI +
  Charts) объявляется в `Package.swift` под `#if canImport(SwiftUI)`. Манифест вычисляется на хосте: на macOS в
  пакете оба таргета, на Linux — только `ChartKitCore` и его тесты. Исходники `ChartKit` условной компиляцией не
  засоряются.
Облачное окружение со Swift не настраивается, облачные треды код ядра не пишут. Оба изменения CI — отдельный тикет
инфраструктуры после merge спеки, вместе с первым тикетом пакетов.
**Почему не:** `xcodebuild test -scheme WeatherCore` в симуляторе — дольше и не нужно: пакеты собираются под macOS
(A-40); облачная разработка ядра — setup-скрипт и тулчейн в каждой сессии, расход лимитов; без Linux — теряется
доказательство «ядро только на Foundation»; `#if canImport(SwiftUI)` вокруг исходников `ChartKit` — условная
компиляция расползается по файлам; отдельный пакет для ядра — ломает E1.
**Основание:** roadmap §4 п. 2; продукт §8 (CI: сборка и тесты); `.github/workflows/ci.yml`; `CLAUDE.md` («код
приложения в облаке не пишется»).
**Как проверяется:** CI — в логе check `test` есть прогон `WeatherCoreTests` и `ChartKitCoreTests`; Linux-job зелёный.
**Пометка:** [Edward] (E3) + тесты пакетов в check `test` [сам: MW-23 K-6]

### A-43. ViewModel и владение состоянием
**Решение:** `@Observable` ViewModel в приложении, изолированные главным актором по умолчанию (A-38):
- `PagerModel` — список страниц, видимая страница, триггеры обновления (A-35);
- `LocationPageModel` — одна на страницу: `PageState`, `ChartViewportModel` почасового графика (своё окно у каждой
  страницы, UX S1), выбор почасового графика (общий, A-45);
- `HistoryModel` — одна на вход в S4: диапазон, вид, `ChartViewportModel`; данные видов «Осадки» и «Ветер»
  загружаются и считаются при открытии вида (UX п. 8).
Зависимости — через инициализатор, включая источник времени `now: () -> Date` (пресеты, «сегодня», TTL, A-48);
корень собирает их в `App` и раздаёт через `Environment` (research §1). Состояние истории — `HistoryState` (A-53).
**Почему не:** одна ViewModel на приложение — смена страницы пересчитывает всё; синглтоны — тесты без подмены.
**Основание:** research §1 (MVVM, `@Observable`, DI); UX S1, S4, §9 п. 8, п. 20.
**Как проверяется:** тесты ViewModel с фейковым репозиторием.
**Пометка:** [сам]

### A-44. Сброс окна графика по событиям

### A-45. Хранение выбора метрик

### A-46. Маппинг домен → серии и единицы

**Почему не:** передать СИ в ядро и форматировать подписи замыканием — деления «некрасивые» в °F и mph.
**Основание:** продукт §7.1; research §5 («единицы, переключаемые пользователем»); UX §9 п. 15, п. 22.
**Как проверяется:** тест — конвертации, единицы по умолчанию для RU, US, GB; смена единиц не вызывает репозиторий.

### A-48. Границы суток, недель, месяцев

### A-49. Агрегации для полос и видов истории
**Решение:** чистые функции `WeatherCore` над `HourlyGrid` и `Calendar` локации:
- суточные полосы min/avg/max + `count` по любой метрике (история > 7 дней, «10 дней» — из почасового прогноза).
  Макс/мин «сегодня» в «Текущей погоде» и в строках S2 — из `daily` прогноза, как решено в UX §6.2 [Edward];
- суммы осадков по суткам, неделям, месяцам; крайние неполные периоды — суммы покрытой части (UX S4);
- «Среднее за период» (UX п. 25) — не агрегация `WeatherCore`, а запрос к индексу: `ChartDataIndex` держит префиксные
  суммы и счётчики исходных (не децимированных) значений, `mean(in: visible, key:)` считается за O(1) синхронно
  на каждой смене `visible`, без задач и их отмены. Появляется после полной загрузки окна (`HistoryState`, A-53).
**Почему не:** полосы из `daily` API — среднего и минимума по всем метрикам там нет, и источник полос разошёлся бы
с почасовым.
**Основание:** продукт §2.3; UX S1, S4, §9 п. 6, п. 25.
**Как проверяется:** тест — агрегации на фикстуре, суммы недель по локали `ru` (понедельник) и `en_US` (воскресенье);

### A-50. Вид «Осадки»
**Решение:** `RainfallChart` в приложении на штатных `chartScrollableAxes(.horizontal)`, `chartXVisibleDomain`,
`chartXSelection` (iOS 17), стартовая позиция — правый край (`chartScrollPosition(initialX:)`). Выбор столбца
«залипает»: `chartXSelection` пишет во временное значение, по его смене с `nil` на дату ViewModel запоминает

Аномалия ≥ 15 мм/сут — только на суточных столбцах.

### A-51. Ветер: агрегация и роза
**Решение:** агрегация — чистая функция `WeatherCore`: 8 секторов по 45° с центром на сторонах света, штиль

**Как проверяется:** тест — секторы на границах 22,5°, штиль, доли в сумме 100 %; хит-тест на краях лепестков.

### A-53. Состояние истории
**Решение:** у `HistoryModel` состояние загрузки — перечисление, общее для трёх видов, по выбранному диапазону:
```swift
enum HistoryState: Sendable {
    case loading(HistorySlice, pending: [DateInterval])                // загруженное + что ещё грузится
    case partial(HistorySlice, failed: [DateInterval])                 // загрузка кончилась, части нет
    case complete(HistorySlice, tail: TailFreshness)                   // .fresh | .stale(since:) — хвост не обновился
    case failed(WeatherError)                                          // ничего нет: кэша нет и сеть упала
}
```
Из состояния выводятся `gaps` для графика и столбцов (`pending` → `.loading`, `failed` → `.failed`) и правила полноты
по видам (UX §6.1, §6.3 [Edward]):

| Вид | `loading` | `partial` | `complete` | `failed` |
|---|---|---|---|---|
| «Метрики» | график с `gaps`, «Среднее» скрыто | график с `gaps .failed`, «Среднее» скрыто | всё, «Среднее» по окну | «Не удалось загрузить историю» + «Повторить» |
| «Осадки» | столбцы со скелетоном, сводки нет | столбцы, «Загружено частично» | «Всего за период» | как «Метрики» |
| «Ветер» | `ProgressView` | **как `failed`** [Edward] | роза со сводкой | как «Метрики» |

`tail: .stale` — баннер под строкой диапазона (UX §6.1, строка S4). Переходы — по событиям `HistoryProgress` из
репозитория (A-34); смена диапазона или вида начинает с `loading`.
**Почему не:** поля `isLoading` / `loadedRanges` / `error` в `HistoryModel` — недопустимые сочетания (P6); отдельное
перечисление на каждый вид — три копии одной загрузки, а различие видов — только в правиле полноты.
**Основание:** UX §6.1 (строки S4), §6.3, §9 п. 2, п. 8; продукт §6.6; P6.
**Как проверяется:** тест ViewModel — последовательность `HistoryProgress` → состояния; «Ветер» при `partial`
показывает отказ; `gaps` выводятся из `pending` и `failed`.
**Пометка:** [сам: MW-23 K-2]
