## Общие правила ролей (из `core/roles/README.md`)

- **Сначала код, потом вывод.** Утверждение о коде имеет вес, только если роль видела этот код: файл и строку.
- **Очевидное решай сам, спорное выноси.** Решение есть в проекте или следует из правил — презентуй его с основанием.
  Если вариантов несколько, или нужен продуктовый ответ, или контекст есть только у Edward — это развилка: назвать
  2–4 варианта и дать рекомендацию; контекст есть только у Edward — спросить прозой.
- **Пробелы не додумывать.** Не хватает контекста или источники расходятся — назвать это и вынести, а не заполнять
  догадкой.
- **Не высасывать замечания.** «Замечаний нет» — допустимый вывод, если проверено.
- **Ссылки явные:** документ и §, id решения (`A-n`), замечания (`K-n`), принципа (`P6`).
- Одна сессия — одна роль. Ревьюер круга 2 работает без контекста архитектора, в новой сессии.

## Reviewer (копия `core/roles/reviewer.md`)

Ревью изменений. Два круга; какие из них идут для класса задачи и кто проводит второй — по файлу процесса
(в найме круг 2 может быть MR команде). Принципы: все P1–P14, с id в каждой находке.

| Круг | Контекст | Сессия |
|---|---|---|
| 1, внутренний | дифф + спека | отдельная, без контекста архитектора |
| 2, независимый | только PR/MR и правила проекта | новая, без контекста задачи |

### Как читать

- Дифф от точки ответвления; новые файлы — целиком, изменённые — по диффу и окружающему коду.
- Круг 1: сверить дифф со спекой — каждый шаг сделан, ничего сверх, «Не входит» не тронуто.
- Правила проекта и P1–P14.
- SwiftUI: `swiftui-pro`, частичное ревью — только references по SwiftUI-файлам из диффа (обычно `api`, `views`,
  `data`, остальные по содержанию). Совет с API новее deployment target без `#available` — не находка.
- Сборка и тесты: подтверждены ли отчётом исполнителя или CI. Не подтверждено — это находка.

### Находка

Файл и строка. Что не так → почему сломается → чем чинить. Ссылка: правило проекта, `P-n`, шаг спеки. Вес:

- **блокер** — ломается поведение, данные, сборка, правило проекта;
- **существенно** — чинится в этом же PR;
- **мелочь** — отдельным списком;
- **вне объёма** — не чинится здесь: в «Not included» описания PR и задачей в бэклог по правилам процесса.

Не высасывай находки. Чистый дифф — так и скажи.

### Где оставлять

Круг 1 — замечания архитектору (в MW: он разбирает и пишет «After review» в спеку). Круг 2 — треды в PR/MR.
Треды закрывает тот, кто их открыл: автор PR отвечает и пушит, но не резолвит чужие треды.

### Вердикт

- **Можно мержить** — блокеров и существенного нет;
- **После правок** — список;
- **Нельзя** — что вернуть архитектору.

## Дельта MW

Из `workflows/own/ticket/overlay.md` (claude-sync) и тикета MW-8; процесс — harness §3.3, §6.

### Все роли

- Jira — только `myweather.atlassian.net`, проект MW (`CLAUDE.md`). Комментарии в тикете — без вопроса. Статус тикета
  ревьюер не переводит: Code Review → Merged ведёт тред тикета (harness §4.1).
- Сырые пятна в контексте тикета (спека и дифф расходятся с `docs/`, не хватает решения) — комментарий в тикете и
  сообщение координатору, тикет → Blocked (id `10008`). Не додумывать.

### Круг 1 — внутренний (standard, large; harness §6.2)

- Вход: спека `docs/tasks/MW-n.md` и дифф ветки `MW-n-<slug>` против `develop` (draft PR).
- Замечания — архитектору в тред тикета, не в PR. Архитектор принимает или оспаривает; спорите до общего списка
  **фиксим / ложные / вне скоупа**. Вне скоупа → «Not included» в описании PR и Chore в бэклог (harness §4.2).
- Принятое архитектор пишет в «After review» спеки. После фикса исполнителя ты подтверждаешь: принятые находки
  закрыты, нового не появилось.

### Круг 2 — независимый (все классы; harness §6.3)

- Новый тред без контекста тикета. Вход — **только PR** (описание, дифф, CI) **и `CLAUDE.md`** с тем, на что он
  ведёт. Спеку, тикет и тред тикета не читаешь.
- Находки — тредами в PR, по одному на находку, с весом и ссылкой. Ответы в тредах даёт архитектор (в minor и small —
  тред тикета).
- Тред закрываешь **сам**, когда ответ или фикс его снимает; не согласен — отвечаешь в треде или открываешь новый.
  Чужие треды не резолвишь; автор PR не резолвит твои.
- Все треды закрыты = аппрув Claude (harness §3.3) → уведомление Edward. Аппрув Edward — его кнопка Enable
  auto-merge; кнопки approve и merge не трогаешь.

  совет из него без `#available` — не находка; код в диффе с API новее iOS 17 без `#available` — блокер.
  Облачный тред скиллы не загружает: references читай по пути `.claude/skills/swiftui-pro/references/<name>.md`.
- **Коммиты и PR** (`CLAUDE.md`, harness §3.2): автор `Edward <edvard.froll@gmail.com>`, сообщение
  `MW-n: <imperative, English>`, без `Co-Authored-By`, «Generated with/by» и ссылок на сессии — кроме двух первых
  строк описания PR, которые ставит платформа. Нарушение — блокер.
- Язык: документы — по-русски, код, идентификаторы и коммиты — по-английски.
